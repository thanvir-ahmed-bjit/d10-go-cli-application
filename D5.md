# D5 Application Guide and Learning Notes

## 1. Overview

D5 is a standalone command-line user-management application written in Go. It stores users in memory while the program is running. It does not use a database, files, web services, or third-party packages.

The application demonstrates structs, pointers, slices, maps, input validation, package responsibilities, terminal formatting, and table-driven unit testing. The program starts with an empty repository. Users disappear when the process exits.

## 2. Project Structure

```text
.
|-- cmd/app/main.go
|-- internal/config/config.go
|-- internal/handler/user_handler.go
|-- internal/model/user.go
|-- internal/repository/user_repository.go
|-- internal/repository/user_repository_test.go
|-- go.mod
|-- D5.md
`-- README.md
```

### Package responsibilities

- `cmd/app/main.go` creates the repository and handler, connects standard input and output, and starts the application. It contains no repository logic.
- `internal/model` defines the `User` data structure.
- `internal/repository` owns all in-memory state and implements create, list, find, update, delete, and filter operations. It never reads or writes terminal data.
- `internal/handler` owns the interactive workflow. It displays the menu, reads input with `bufio.Scanner`, validates values, calls repository methods, and formats output.
- `internal/config` stores small application constants such as the menu heading.
- `user_repository_test.go` contains table-driven tests for repository behavior.

The dependency direction is intentionally simple:

```text
main -> handler -> repository -> model
                 -> config
```

This separation keeps storage independent from terminal behavior and makes the repository easy to test.

## 3. Startup and Data Flow

The startup sequence is:

1. `main` calls `repository.NewUserRepository()`.
2. The constructor initializes an empty map with `make`.
3. `main` passes the repository, `os.Stdin`, and `os.Stdout` to the handler.
4. `Run` displays the menu repeatedly.
5. The handler validates input and delegates state changes to the repository.
6. The handler prints the result and returns to the menu.
7. Selecting option 7, or reaching end-of-input, prints `Goodbye!` and exits normally.

### One menu cycle

Each loop iteration writes the menu to the configured output writer and reads one trimmed line from the scanner. The `switch` statement selects exactly one operation. An operation either completes, reports an error, or stops because input ended; after a normal operation, the loop starts again and prints the menu.

For ID-based operations, `readID` converts the text with `strconv.Atoi`. If conversion fails, it prints an error and returns `false`, so the current operation is cancelled without changing repository state. The next loop iteration still shows the menu. If `Scanner.Scan` returns `false`, the handler treats it as end-of-input and exits gracefully.

## 4. User Model

The model is deliberately small:

```go
type User struct {
    ID    int
    Name  string
    Email string
}
```

The ID identifies a user and must be unique. Name and email are required text fields. The repository stores pointers to these structs so the ordered slice and ID map refer to the same user object.

## 5. Repository State

The repository maintains two indexes:

```go
usersByOrder []*model.User
usersByID    map[int]*model.User
```

`usersByOrder` preserves insertion order. This matters because map iteration does not guarantee a stable display order. `usersByID` provides fast average lookup by integer ID.

Both collections contain pointers to the same user objects. They are two indexes over one logical set of users, so every create, update, and delete operation must keep both indexes synchronized.

### Repository invariant

For every user in `usersByOrder`, `usersByID[user.ID]` must point to that same user. The reverse relationship must also hold: every map entry must point to a user present in the ordered slice. The repository methods are the only place that mutate these collections, which gives them one clear owner for maintaining this invariant.

## 6. Repository Operations

### Create

`Create` rejects a nil user pointer, a name that is empty after trimming whitespace, an empty email, and a duplicate ID. A successful create appends the pointer to `usersByOrder` and stores the same pointer in `usersByID`.

The repository returns meaningful errors for normal validation failures:

- `ErrDuplicateID`
- `ErrEmptyName`
- `ErrEmptyEmail`

### List

`List` creates a new slice and copies the repository's slice into it. This prevents callers from changing the repository's slice structure by reordering or appending to the returned slice. The copied slice still contains pointers to the current user objects.

This is a shallow copy of the collection, not a deep copy of every user. A caller cannot change the repository's slice length or order through the result, but it can observe the same pointed-to user values. Updates performed by the repository are therefore visible in previously returned user pointers.

The handler formats non-empty results as a terminal table. Empty results produce `No users found.`.

### Find

`Find` uses direct map lookup rather than scanning the ordered slice. It returns a user pointer and a boolean indicating whether the ID exists:

```go
user, exists := r.usersByID[id]
```

### Update

`Update` first checks that the ID exists, then validates the replacement name and email. It changes the fields on the shared user pointer. Because both collections point to that object, the updated values are visible through both the map and the ordered slice.

### Delete

`Delete` verifies the ID, locates the user in the ordered slice, and shifts later elements left:

```go
copy(r.usersByOrder[index:], r.usersByOrder[index+1:])
```

It then clears the unused final pointer slot and shortens the slice:

```go
lastIndex := len(r.usersByOrder) - 1
r.usersByOrder[lastIndex] = nil
r.usersByOrder = r.usersByOrder[:lastIndex]
```

Finally, it removes the ID from the map. Shifting preserves the relative order of all remaining users. Deletion is $O(n)$ because the slice may need to be shifted; this is the tradeoff for preserving order.

Find, duplicate detection, and the initial delete-existence check use average $O(1)$ map operations. List is $O(n)$ because it copies the slice header entries, while filter is $O(n)$ because it checks each user. The repository does not optimize for persistence or concurrent access because its state is intentionally process-local and used by one CLI flow.

### Filter

`Filter` creates a new result slice and checks every user in insertion order. It trims and lowercases the search term, then performs case-insensitive partial matching against both the name and email. The repository state is not changed. Filtering is $O(n)$ because every user may need to be inspected.

## 7. CLI Workflow

The handler repeatedly displays the following menu:

```text
1. Add user
2. List users
3. Find user by ID
4. Update user
5. Delete user
6. Filter users
7. Exit
```

After each operation, control returns to the menu. An invalid menu option produces a friendly message and does not terminate the application.

The handler uses `bufio.Scanner` to read one line at a time. `readLine` trims whitespace. `readID` calls `strconv.Atoi` and reports `Invalid integer input.` when conversion fails.

### Add user

The handler reads an ID, name, and email, creates a `model.User`, and calls `Create`. Duplicate IDs and empty text are rejected.

### List users

The handler calls `List` and displays users in insertion order. A friendly message is shown when there are no users.

### Find user by ID

The handler validates the ID, calls `Find`, and displays either the matching user or a missing-user error.

### Update user

The handler reads an existing ID, a new name, and a new email, then calls `Update`. The user remains in its original position.

### Delete user

The handler validates the ID and calls `Delete`. Remaining users keep their relative insertion order.

### Filter users

The handler reads a search term and displays users whose name or email contains that term, ignoring case.

Filtering returns a new result slice, so filtering does not remove or reorder users in the repository. Like `List`, the result contains pointers to the existing user objects rather than independent user copies.

### Exit

The handler prints `Goodbye!` and returns from `Run`, allowing `main` to terminate the process normally.

## 8. Error Handling

Normal validation problems are represented as errors rather than panics:

| Situation | Behavior |
|---|---|
| Invalid menu option | Print a menu error and continue |
| Non-integer ID | Print `Invalid integer input.` |
| Duplicate ID | Return `ErrDuplicateID` |
| Missing user | Return `ErrUserNotFound` |
| Empty name | Return `ErrEmptyName` |
| Empty email | Return `ErrEmptyEmail` |
| End of input | Print goodbye and exit gracefully |

The application does not use `panic` for expected user mistakes.

## 9. Go Concepts Used by D5

The complete lessons on these topics are in the Day 4 guide, [D4.md](D4.md). D5 applies them in one working application rather than repeating the general tutorials.

### Arrays versus slices

An array has a fixed length, while a slice is a resizable view over backing storage. D5 uses `[]*model.User` because the number of users changes during a session.

### Length, capacity, and backing arrays

For the repository slice, `len` reports the current number of users and `cap` reports the slice's capacity. `append` adds users and may allocate a new backing array. `List` copies the slice structure so callers cannot reorder the repository's internal slice, while the copied elements still point to the same users.

### Inserting and deleting slice elements

D5 appends new users. The delete operation shifts later pointers left to preserve insertion order, clears the unused final pointer slot, and then reduces the slice length:

```go
copy(r.usersByOrder[index:], r.usersByOrder[index+1:])
lastIndex := len(r.usersByOrder) - 1
r.usersByOrder[lastIndex] = nil
r.usersByOrder = r.usersByOrder[:lastIndex]
```

An unordered swap-with-last deletion would be faster, but it would violate D5's ordered-list requirement.

### Maps and comma-ok lookup

The map uses user IDs as keys for fast lookup. `Find` uses the comma-ok form to distinguish a missing ID from a stored pointer:

```go
user, exists := r.usersByID[id]
```

### Nil maps

Reading from a nil map is safe, but writing to one panics. `NewUserRepository` initializes `usersByID` with `make`, so create operations are safe.

### Slice and map synchronization

The repository maintains one invariant: both indexes describe the same users.

| Operation | Ordered slice | ID map |
|---|---|---|
| Create | Append the user pointer | Assign `id -> pointer` |
| Update | Shared pointer sees new fields | Shared pointer sees new fields |
| Delete | Shift, clear, and shorten | Delete the ID |

### Pointer behavior

D5 stores `*model.User`, so the slice and map refer to the same user object. Updating the object through the map is visible through the slice. `Create` rejects nil pointers before reading user fields, and `Delete` clears the removed pointer from the backing array.

## 10. Testing Strategy

The repository tests use a table-driven structure. Each test case has a name, optional setup function, and test function. A fresh repository is created for every case, so tests do not share state.

The tests cover:

- Adding a valid user.
- Rejecting a duplicate ID.
- Finding an existing user.
- Finding a missing user.
- Updating an existing user.
- Updating a missing user.
- Deleting a user.
- Preserving slice order after deletion.
- Filtering by name.
- Filtering by email.
- Confirming that the slice and map remain synchronized.

The tests use repository package access so they can inspect the internal map length when verifying deletion. Each test starts with `NewUserRepository`, which prevents one scenario from depending on another. The table-driven form keeps the setup pattern consistent while giving each behavior a descriptive test name.

Run the tests from the project root:

```powershell
go test ./...
```

## 11. Running the Application

From `D:\1go\d5-go-cli-application`, run:

```powershell

```


The module name is `d5`, and all imports are internal to this standalone module. The application uses only the Go standard library.

## 13. Summary

D5 demonstrates a focused Go design: the model defines data, the repository owns synchronized in-memory state, the handler owns terminal interaction, and `main` wires the pieces together. The ordered slice gives predictable display order, the map gives fast ID lookup, and pointers allow both structures to refer to the same user records. Tests protect repository behavior while the application remains easy to run, inspect, and extend.
