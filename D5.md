# D5 Learning Notes: Slices, Maps, and User State

## Arrays versus Slices

An array has a fixed length that is part of its type, such as `[3]string`. A slice is a small descriptor over a variable-length sequence, such as `[]string`. Slices are usually the practical choice for collections that grow while a program runs.

## Slice Length and Capacity

`len(slice)` is the number of elements currently in the slice. `cap(slice)` is how many elements fit in its current backing storage before Go needs to allocate a new backing array. `append` increases length and may increase capacity.

## Backing Arrays

A slice does not contain the entire array value. It points to backing storage and tracks a length and capacity. Two slices can share backing storage, so changes through one slice can be visible through another. The repository returns a copied slice header so callers cannot reorder its internal slice, while its user pointers still refer to the stored users.

## Inserting and Deleting Slice Elements

To delete an element while preserving order, copy the elements after it one position left:

```go
copy(items[index:], items[index+1:])
items[len(items)-1] = nil
items = items[:len(items)-1]
```

The final assignment clears an unused pointer slot before the slice length shrinks. This helps the garbage collector release an object when no other pointer refers to it.

## Maps and Comma-Ok Lookup

The expression `user, exists := usersByID[id]` uses Go's comma-ok idiom. `exists` is false when the key is absent, even though the value receives the type's zero value. This lets the repository distinguish a missing user from a stored pointer.

## Nil Maps

A nil map can be read from and deleted from, but assigning a key to it panics. `NewUserRepository` creates the map with `make`, so every repository is ready for writes.

## Slice and Map Synchronization

D5 keeps two views of the same users:

- `usersByOrder` stores pointers in insertion order.
- `usersByID` maps each ID to the same pointer.

Create appends and assigns. Update changes the shared user pointer, so both views see the new fields. Delete removes the pointer from the ordered slice and deletes the same ID from the map. Keeping those operations together prevents stale state.

## Pointer Behavior

The repository stores `*model.User` values. The slice and map therefore point to the same user object. Updating its fields through the map also updates the object observed through the slice. Pointers avoid copying the whole struct and make shared state explicit.

## How the D5 Application Works

`main.go` creates the repository, connects it to a handler, and starts `Run`. The handler repeatedly prints the seven-option menu, scans one line at a time, validates IDs and text, and calls the repository. The repository returns errors such as duplicate ID, missing user, empty name, or empty email. The handler turns those errors into terminal messages and then shows the menu again.

Filtering creates a new result slice. It lowercases both the search term and each user's name and email, allowing case-insensitive partial matches without changing repository state.
