# 2. Arrays versus slices

> **Explanation:** Arrays and slices may look similar when indexed, but their semantics are different. An array owns a fixed number of elements and is copied as a complete value. A slice is a small descriptor that provides access to part or all of an underlying array.

An array has a fixed length, and its length is part of its type. A slice is a dynamic view over an underlying array.

```go
var array = [3]int{10, 20, 30}
slice := []int{10, 20, 30}

fmt.Println(len(array)) // 3
fmt.Println(len(slice)) // 3
```

| Feature | Array | Slice |
|---|---|---|
| Length | Fixed and part of the type | Dynamic view |
| Assignment | Copies all elements | Copies the slice descriptor |
| Function parameter | Copies the complete array | Copies a small descriptor |
| Comparison | Comparable with the same array type | Can only be compared with `nil` |

# 3. Slice internal header semantics

> **Explanation:** A slice can be understood as a descriptor containing a data pointer, a length, and a capacity. Copying the descriptor is inexpensive, but the copied slices may still reach the same elements, which is why mutations can appear through multiple variables.

Conceptually, a slice contains three pieces of information:

```go
type conceptualSliceHeader struct {
    Data *T
    Len  int
    Cap  int
}
```

This is a mental model. It is not a public generic struct that application code should depend on.

- **Data pointer:** Points to the first slice element in the backing array.
- **Length:** Number of elements currently accessible through the slice.
- **Capacity:** Maximum range available from the slice's starting position without allocating another backing array.

### Header copy and shared data

Assigning one slice to another copies the slice descriptor, not the elements.

```go
numbers := []int{10, 20, 30}
alias := numbers

alias[0] = 99

fmt.Println(numbers) // [99 20 30]
```

Both slices point to the same backing array, so an element mutation through one slice is visible through the other.

# 4. Length, capacity, reslicing, and aliasing

> **Explanation:** Length controls the indexes currently available through a slice. Capacity controls how far that slice can be extended from its starting position without allocating another array. Aliasing occurs when different slices refer to overlapping regions of the same backing array.

```go
base := []int{10, 20, 30, 40, 50}
part := base[1:3]

fmt.Println(part)      // [20 30]
fmt.Println(len(part)) // 2
fmt.Println(cap(part)) // 4
```

The slice starts at index 1 of `base`. Its length is 2, but its capacity is 4 because four elements remain between its starting position and the end of the backing array.

```go
part[0] = 200
fmt.Println(base) // [10 200 30 40 50]
```

**Caution:** If independent data is required, create a new destination and copy the elements.

# 5. Creating slices with make

> **Explanation:** The make function initializes the runtime data structure required by a slice. The length creates immediately accessible elements initialized to their zero values, while the optional capacity reserves room for future growth.

```go
a := make([]int, 3)     // len=3, cap=3, values=[0 0 0]
b := make([]int, 0, 10) // len=0, cap=10

b = append(b, 5)
```

Use:

```go
make([]T, length, capacity)
```

Preallocating a reasonable capacity can reduce repeated allocations when the approximate number of elements is already known.

# 6. append and capacity growth

> **Explanation:** The append function may reuse the current backing array or allocate another one. Because the returned descriptor can point somewhere new and can contain a different length and capacity, callers must use the returned slice.

`append` returns a slice. It may reuse the existing backing array when capacity is sufficient, or allocate a new backing array when more capacity is needed.

Always assign or otherwise use the returned slice:

```go
numbers := []int{1, 2}
numbers = append(numbers, 3)
```

### When append separates two slices

```go
base := make([]int, 2, 2)
base[0], base[1] = 10, 20

alias := base
base = append(base, 30) // requires more capacity
base[0] = 99

fmt.Println(base)  // [99 20 30]
fmt.Println(alias) // [10 20]
```

After `append`, `base` points to a new backing array, while `alias` still points to the old one.

**Important:** The exact capacity-growth strategy is an implementation detail. Do not build application logic around an assumed doubling rule.

# 7. Copying slices safely

> **Explanation:** Assigning a slice copies only its descriptor. Use copy, slices.Clone, or another explicit cloning pattern when the destination must be independent from later source mutations.

```go
source := []int{10, 20, 30}
destination := make([]int, len(source))

count := copy(destination, source)

fmt.Println(count)       // 3
fmt.Println(destination) // [10 20 30]
```

`copy(dst, src)` returns the number of elements copied:

```text
min(len(destination), len(source))
```

A common cloning pattern is:

```go
clone := append([]int(nil), source...)
```

With Go 1.21 or later:

```go
clone := slices.Clone(source)
```

# 8. Common slice manipulations

> **Explanation:** Go intentionally provides a small set of primitive slice operations. Insert, delete, filter, and reverse operations are built by combining slicing, append, copy, and index assignment. Each implementation must define its index policy, order requirement, allocation behavior, and memory-retention behavior.

### 8.1 Insert an element

```go
numbers := []int{10, 20, 30}
index := 1
value := 15

numbers = append(numbers, 0)
copy(numbers[index+1:], numbers[index:])
numbers[index] = value

fmt.Println(numbers) // [10 15 20 30]
```

Validate the index before performing the operation.

### 8.2 Delete while preserving order

```go
index := 1
numbers = append(numbers[:index], numbers[index+1:]...)
```

This is usually **O(n)** because later elements may need to move.

For a slice containing pointers, clear the unused final slot when retaining the backing array could keep an object alive unnecessarily:

```go
copy(items[index:], items[index+1:])
items[len(items)-1] = nil
items = items[:len(items)-1]
```

### 8.3 Delete without preserving order

When order does not matter:

```go
numbers[index] = numbers[len(numbers)-1]
numbers = numbers[:len(numbers)-1]
```

This operation is **O(1)**.

### 8.4 Filter in place

```go
numbers := []int{1, 2, 3, 4, 5, 6}
evenNumbers := numbers[:0]

for _, number := range numbers {
    if number%2 == 0 {
        evenNumbers = append(evenNumbers, number)
    }
}

fmt.Println(evenNumbers) // [2 4 6]
```

This reuses the original backing array.

### 8.5 Reverse a slice

```go
for left, right := 0, len(numbers)-1; left < right; left, right = left+1, right-1 {
    numbers[left], numbers[right] = numbers[right], numbers[left]
}
```

# 9. nil slice versus empty slice

> **Explanation:** A nil slice and an initialized empty slice both have zero length and can be ranged over or appended to. They differ in nil comparison and may serialize differently, which can affect API contracts and persistence formats.

```go
var nilSlice []int
emptySlice := []int{}

fmt.Println(nilSlice == nil)   // true
fmt.Println(emptySlice == nil) // false

fmt.Println(len(nilSlice))   // 0
fmt.Println(len(emptySlice)) // 0
```

Both support:

- `len`
- `range`
- `append`

However, serialization can differ. For example, JSON encoding commonly represents a nil slice as `null` and an initialized empty slice as `[]`.

# 10. range behavior with slices

> **Explanation:** When ranging over a slice, the value variable receives a copy of the current element. Mutating that local variable does not update the slice. Use the index when the original element must change.

The value variable produced by `range` is a copy.

```go
numbers := []int{10, 20, 30}

for _, value := range numbers {
    value *= 2
}

fmt.Println(numbers) // [10 20 30]
```

Use the index to modify actual elements:

```go
for index := range numbers {
    numbers[index] *= 2
}

fmt.Println(numbers) // [20 40 60]
```

Be careful when appending to or deleting from the same slice during iteration. A separate-result pattern is often easier to reason about.

# 11. Creating and indexing maps

> **Explanation:** A map associates comparable keys with values. Reading an absent key produces the value type zero value. A nil map can be read but cannot accept assignments, so initialize it with a literal or make before writing.

```go
scores := map[string]int{
    "Asha": 90,
    "Rafi": 85,
}

fmt.Println(scores["Asha"]) // 90
```

A map can also be initialized with `make`:

```go
scores := make(map[string]int)
scores["Asha"] = 90
```

### nil map behavior

```go
var counts map[string]int

fmt.Println(counts["go"]) // 0
```

Reading from a nil map is safe. Writing to it causes a panic:

```go
// counts["go"] = 1
// panic: assignment to entry in nil map
```

Initialize it before writing:

```go
counts = make(map[string]int)
counts["go"] = 1
```

# 12. Safe map lookup: comma-ok idiom

> **Explanation:** The comma-ok form returns both the value and an existence flag. It is necessary whenever a legitimate stored value can equal the type zero value, such as stock level 0, false, or an empty string.

```go
score, exists := scores["Nadia"]

if !exists {
    fmt.Println("key is missing")
} else {
    fmt.Println(score)
}
```

A simple lookup returns the value type's zero value when the key is missing. That can be ambiguous:

```go
stock := map[string]int{
    "pen": 0,
}

penStock := stock["pen"]   // 0, key exists
bookStock := stock["book"] // 0, key is missing

_, penExists := stock["pen"]   // true
_, bookExists := stock["book"] // false
```

Use comma-ok whenever zero is a valid stored value and the distinction matters.

# 13. Map updates, counters, and deletion

> **Explanation:** Map indexing can appear on the left side of an assignment, which makes counters and accumulators concise. The delete function safely removes a key and has no effect when the key is already absent.

```go
frequencies := make(map[string]int)

for _, word := range []string{"go", "java", "go"} {
    frequencies[word]++
}

fmt.Println(frequencies["go"]) // 2
```

A missing numeric key starts with its zero value, so `frequencies[word]++` works naturally.

Delete a key with:

```go
delete(frequencies, "java")
```

Deleting a missing key is safe and does nothing.

# 14. Map rules and pitfalls

> **Explanation:** Map keys must support equality, iteration order is deliberately unspecified, and map assignment shares access to the same underlying data. These rules affect API design, deterministic output, testing, and mutation visibility.

### Iteration order

Map iteration order is unspecified. Never make business logic depend on it.

For deterministic output:

```go
keys := make([]string, 0, len(scores))

for key := range scores {
    keys = append(keys, key)
}

sort.Strings(keys)

for _, key := range keys {
    fmt.Println(key, scores[key])
}
```

### Valid key types

Map keys must be comparable.

Common valid key types:

- Strings
- Integers
- Booleans
- Pointers
- Channels
- Comparable arrays
- Structs whose fields are all comparable

Slices, maps, and functions cannot be map keys.

### Assignment behavior

Assigning a map variable copies a small descriptor. Both variables refer to the same underlying map data.

```go
first := map[string]int{"go": 1}
second := first

second["go"] = 2

fmt.Println(first["go"]) // 2
```

# 15. Struct values stored in maps

> **Explanation:** A map element is not addressable because map growth and reorganization may move entries internally. Retrieve a struct value, modify the copy, and store it again; alternatively, store pointers only when shared mutable objects are intentional.

Map elements are not addressable.

```go
type User struct {
    Name   string
    Active bool
}

users := map[int]User{
    1: {Name: "Asha", Active: false},
}
```

This does not compile:

```go
// users[1].Active = true
```

Retrieve, modify, and assign the value back:

```go
user := users[1]
user.Active = true
users[1] = user
```

Alternatively, store pointers intentionally:

```go
users := map[int]*User{
    1: {Name: "Asha"},
}

users[1].Active = true
```

The pointer approach introduces shared mutation and possible nil values, so use it deliberately.

# 16. Concurrent map access

> **Explanation:** Ordinary maps do not provide synchronization for concurrent access involving writes. Protect shared access with a mutex, confine ownership to one goroutine, or use sync.Map only when its specialized behavior fits the workload.

A built-in map is not safe for unsynchronized concurrent access involving writes.

```go
type SafeCounter struct {
    mu sync.RWMutex
    m  map[string]int
}

func (counter *SafeCounter) Increment(key string) {
    counter.mu.Lock()
    defer counter.mu.Unlock()

    counter.m[key]++
}

func (counter *SafeCounter) Get(key string) int {
    counter.mu.RLock()
    defer counter.mu.RUnlock()

    return counter.m[key]
}
```

A typed map protected by `sync.RWMutex` is usually clear for known key and value types. Consider `sync.Map` for specialized workloads, especially some read-mostly or dynamic-key scenarios.

# 17. Pointers with functions

> **Explanation:** Go passes every argument by value. Passing a pointer copies the address, not the complete pointed-to object. The copied pointer still identifies the same object, allowing the function to mutate that object indirectly.

Go always passes arguments by value.

When a pointer is passed, the pointer value—the address—is copied. The copied pointer still refers to the same underlying value, so the function can modify it indirectly.

```go
type Account struct {
    Balance float64
}

func Deposit(account *Account, amount float64) error {
    if account == nil {
        return fmt.Errorf("account is nil")
    }

    if amount <= 0 {
        return fmt.Errorf("amount must be positive")
    }

    account.Balance += amount
    return nil
}
```

Usage:

```go
account := Account{
    Balance: 1000,
}

if err := Deposit(&account, 500); err != nil {
    fmt.Println("Error:", err)
    return
}

fmt.Println(account.Balance) // 1500
```

The following two expressions are equivalent for a struct pointer:

```go
account.Balance += amount
(*account).Balance += amount
```

Go automatically dereferences the pointer for field selection.

**Precise statement:** Go is pass-by-value. Passing a pointer copies an address and permits indirect mutation. Avoid saying that Go supports pass-by-reference.

# 18. Value parameter versus pointer parameter

> **Explanation:** Choose a parameter type according to meaning rather than habit. Value parameters communicate copy-like or read-only semantics, while pointer parameters communicate possible mutation, shared identity, nil, or avoidance of a significant copy.

```go
func RenameValue(user User, name string) {
    user.Name = name
}

func RenamePointer(user *User, name string) {
    if user != nil {
        user.Name = name
    }
}
```

| Decision | Prefer a value | Prefer a pointer |
|---|---|---|
| Mutation | Caller value should remain unchanged | Caller value must be updated |
| Size | Small value or struct | Avoid copying a large struct |
| Nil | Nil is not meaningful | Nil is meaningful or possible |
| Ownership | An independent copy is desired | Shared state is intentional |
| Methods | Type consistently uses value receivers | Type consistently uses pointer receivers |

Do not choose a pointer automatically for every struct. Make the decision based on semantics, size, consistency, and API clarity.

# 19. Do slices and maps need pointer parameters?

> **Explanation:** Slices and maps already use small descriptors that refer to runtime-managed data. Their elements can normally be updated without pointers to the descriptor. Return an updated slice when append may change its descriptor.

Slices and maps already have reference-like behavior through their descriptors. A pointer to a slice or map is usually unnecessary for ordinary element updates.

### Slice

```go
func Add(items []int, value int) []int {
    return append(items, value)
}
```

Returning the updated slice is clearer because `append` may replace the slice header.

### Map

```go
func Count(frequencies map[string]int, key string) {
    frequencies[key]++
}
```

The function can update map entries without receiving `*map[string]int`.

A pointer to a slice may be justified when a function intentionally replaces the caller's slice header without returning it, but returning the slice is normally easier to understand.

# 20. Integrated inventory example

> **Explanation:** The inventory example combines the D4 concepts in a small domain model: constructor-based map initialization, duplicate detection, comma-ok lookup, pointer-based product mutation, input validation, and explicit errors for expected failures.

```go
type Product struct {
    ID    string
    Stock int
}

type Inventory struct {
    items map[string]*Product
}

func NewInventory(capacity int) *Inventory {
    return &Inventory{
        items: make(map[string]*Product, capacity),
    }
}

func (inventory *Inventory) Add(product Product) error {
    if product.ID == "" {
        return fmt.Errorf("product ID is required")
    }

    if _, exists := inventory.items[product.ID]; exists {
        return fmt.Errorf("product %s already exists", product.ID)
    }

    productCopy := product
    inventory.items[product.ID] = &productCopy
    return nil
}

func (inventory *Inventory) IncreaseStock(id string, amount int) error {
    if amount <= 0 {
        return fmt.Errorf("amount must be positive")
    }

    product, exists := inventory.items[id]
    if !exists {
        return fmt.Errorf("product %s not found", id)
    }

    product.Stock += amount
    return nil
}
```

This example combines:

- Constructor-based map initialization
- Safe comma-ok lookup
- Pointer-based mutation
- Duplicate validation
- Errors for expected failures

# 21. Complexity reference

> **Explanation:** Complexity explains how work grows with input size. Slice indexing is constant time, but ordered insertion and deletion may shift many elements. Map access is typically constant time on average, while sorting map keys adds an O(n log n) step.

| Operation | Typical complexity | Reason |
|---|---:|---|
| Slice index | O(1) | Direct offset access |
| Slice append | Amortized O(1) | Occasional allocation and copying |
| Ordered slice insertion | O(n) | Elements may shift |
| Ordered slice deletion | O(n) | Elements may shift |
| Unordered slice deletion | O(1) | Replace with final element |
| Slice copy | O(n) | Elements are copied |
| Map get/put/delete | Average O(1) | Hash-based lookup |
| Sort map keys | O(n log n) | Sorting for deterministic output |

# 22. Interview questions and answers

> **Explanation:** Use these questions to practice concise technical communication. A strong answer states the rule, explains the reason, and gives a small consequence or example without overstating implementation details.

### Q1. What is a slice?

A slice is a dynamic view over an underlying array. Conceptually, it contains a pointer, a length, and a capacity.

### Q2. Does assigning a slice copy its elements?

No. Assignment copies the slice descriptor. Both slices may still share the same backing array.

### Q3. Why must the result of append be assigned?

Because `append` may return a new slice descriptor that points to a newly allocated backing array.

### Q4. What is the difference between len and cap?

`len` is the number of elements currently accessible through the slice. `cap` is the maximum reslice range from the current starting position without another allocation.

### Q5. What is the difference between a nil slice and an empty slice?

Both have length zero and support `append` and `range`. Only the nil slice compares equal to `nil`, and their serialized forms may differ.

### Q6. How do you distinguish a missing map key from a stored zero value?

Use the comma-ok idiom:

```go
value, exists := data[key]
```

### Q7. Can you write to a nil map?

No. Reading is safe, but writing causes a panic. Initialize the map with `make` or a map literal.

### Q8. Is map iteration ordered?

No. Collect and sort the keys when deterministic order is required.

### Q9. Are maps concurrency-safe?

Not for unsynchronized concurrent access involving writes. Use a mutex, single-goroutine ownership, or `sync.Map` where appropriate.

### Q10. Is Go pass-by-reference?

No. Go is pass-by-value. A pointer argument is a copied address that permits indirect mutation.

### Q11. When should a function receive a pointer?

Use a pointer when mutation is intentional, copying a large value should be avoided, nil has meaning, or the type consistently uses pointer receivers.

### Q12. Why can a map's struct field not be modified directly?

Map elements are not addressable. Retrieve the struct, modify the copy, and assign it back, or intentionally store pointers.

## Modernization notes

- Do not use unsafe or reflect-based slice-header manipulation in normal application code.
- Do not assume an exact append capacity-growth factor.
- Use three-index slicing when capacity must be restricted intentionally.
- Prefer package slices helpers when they improve clarity.
- Map iteration order is unspecified; sort keys for deterministic output.
- Maps require synchronization for concurrent access involving writes.
- Go is pass-by-value; a pointer is a copied address permitting indirect mutation.

## Practice implementation in `cmd/d4-sample`

A runnable sample program that demonstrates all core D4 concepts is available in `cmd/d4-sample/main.go`. This includes:

- Array value semantics versus slice descriptor behavior
- Slice header semantics and aliasing through the backing array
- Append, capacity growth, and reallocation
- Three-index slicing to prevent unintended aliasing
- Copy and clear operations
- Safe slice insertion, deletion, and filtering using package slices
- Map initialization, lookup, mutation, and deletion
- Map iteration and iteration-order implications
- Value and pointer parameters and their semantics
- Slice and map behavior when passed to functions

Run every sample with:

```bash
go run ./cmd/d4-sample
```

The sample output demonstrates:

- How mutations in one slice descriptor affect other slices pointing to the same backing array
- Capacity-growth behavior during append operations
- Three-index slicing preventing accidental aliasing after append
- Map entry lookup with the comma-ok idiom
- The distinction between value and pointer parameters
- How slices and maps behave differently as function parameters
