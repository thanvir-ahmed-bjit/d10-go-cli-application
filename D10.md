## 1. Learning Goal and Acceptance Criteria

Refactor the Week 1 user-management CLI into clean, object-oriented Go code with explicit dependencies, custom error handling, concurrency-safe state, and a background logging goroutine.

By the end of D10, the application should:

- preserve the existing add, list, find, update, delete, and filter operations;
- organize responsibilities using structs, methods, constructors, and small interfaces;
- introduce a service layer between the CLI handler and repository;
- protect shared in-memory state from data races;
- represent domain failures with sentinel and custom typed errors;
- send log events to a dedicated background goroutine;
- shut down the logger without losing accepted messages or leaking goroutines;
- support unit tests through dependency injection;
- pass formatting, tests, static analysis, and race detection.

## 2. Existing Application Review

The attached project is a useful Week 1 baseline. Its current flow is:

```text
cmd/app/main.go
    -> UserHandler
        -> UserRepository
            -> []\*User + map[int]\*User
```

Current strengths:

- the entry point is small;
- the model, handler, repository, and configuration are separated;
- the repository preserves insertion order with a slice and performs fast ID lookup with a map;
- input and output use `io.Reader` and `io.Writer`, which helps testing;
- repository behavior already has table-driven tests.

Required D10 improvements:

- rename the module and application identity from `d5` to `d10-go-cli-application`;
- remove direct handler-to-concrete-repository coupling;
- add a service layer for application behavior;
- add synchronization because the repository may be accessed concurrently;
- replace generic validation errors with structured errors where callers need details;
- add an asynchronous logger with an explicit lifecycle;
- propagate `context.Context` through potentially blocking operations;
- add handler, service, logger, and concurrency tests.

## 3. Object-Oriented Design in Go

Go is not class-based, but it supports object-oriented design through:

- **structs** for state;
- **methods** for behavior;
- **constructors** for valid initialization;
- **interfaces** for abstractions;
- **encapsulation** through exported and unexported identifiers;
- **composition** instead of class inheritance.

```go
type UserService struct {
	repository UserRepository
	logger     Logger
}

func NewUserService(repository UserRepository, logger Logger) *UserService {
	return &UserService{repository: repository, logger: logger}
}
```

`UserService` owns its dependencies as fields, while `NewUserService` constructs a usable service. The service depends on interfaces rather than concrete implementations.

## 5. Repository Interface

The service should depend on the behavior it needs:

```go
type UserRepository interface {
	Create(ctx context.Context, user *model.User) error
	List(ctx context.Context) ([]*model.User, error)
	Find(ctx context.Context, id int) (*model.User, error)
	Update(ctx context.Context, id int, name, email string) error
	Delete(ctx context.Context, id int) error
	Filter(ctx context.Context, term string) ([]*model.User, error)
}
```

The in-memory repository implements this interface implicitly. The service can therefore use the real repository in production and a fake repository in tests.

Add a compile-time check:

```go
var _ UserRepository = (*MemoryUserRepository)(nil)
```

This produces no useful runtime value. Compilation fails if `MemoryUserRepository` stops satisfying the interface.

## 6. Concurrency-Safe Repository

The attached repository contains a slice and a map. Concurrent reads and writes must be synchronized.

```go
type MemoryUserRepository struct {
	mu           sync.RWMutex
	usersByOrder []*model.User
	usersByID    map[int]*model.User
}
```

Use a write lock for mutations:

```go
r.mu.Lock()
defer r.mu.Unlock()
```

Use a read lock for read-only operations:

```go
r.mu.RLock()
defer r.mu.RUnlock()
```

Return copies instead of internal pointers when practical. Otherwise, a caller could mutate a user after the repository lock has been released and create a race.

```go
func cloneUser(user *model.User) *model.User {
	if user == nil {
		return nil
	}
	copy := *user
	return &copy
}
```

## 7. Service Layer

The service represents application use cases and keeps business decisions out of the terminal handler.

```go
type UserService struct {
	repository UserRepository
	logger     Logger
}

func (s *UserService) Create(ctx context.Context, user *model.User) error {
	if err := s.repository.Create(ctx, user); err != nil {
		return fmt.Errorf("create user %d: %w", user.ID, err)
	}

	s.logger.Log(ctx, fmt.Sprintf("user %d created", user.ID))
	return nil
}
```

The service:

1. receives a use-case request;
2. calls the repository;
3. wraps failures with useful context;
4. submits a log event;
5. returns a result to the handler.

## 8. Sentinel and Custom Errors

Use a sentinel error when callers only need to recognize a stable condition:

```go
var (
	ErrDuplicateID  = errors.New("duplicate user ID")
	ErrUserNotFound = errors.New("user not found")
)
```

Use a custom type when callers need structured information:

```go
type ValidationError struct {
	Field  string
	Reason string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("invalid %s: %s", e.Field, e.Reason)
}
```

Return it as a pointer:

```go
return &ValidationError{Field: "email", Reason: "cannot be empty"}
```

Inspect known errors with `errors.Is`:

```go
if errors.Is(err, domain.ErrUserNotFound) {
	fmt.Fprintln(output, "User not found.")
}
```

Extract structured errors with `errors.As`:

```go
var validationErr *domain.ValidationError
if errors.As(err, &validationErr) {
	fmt.Fprintf(output, "Invalid %s: %s\n", validationErr.Field, validationErr.Reason)
}
```

Always wrap a cause with `%w` when callers must still inspect it:

```go
return fmt.Errorf("update user %d: %w", id, err)
```

## 9. Background Logging Goroutine

The asynchronous logger accepts messages through a channel and writes them from one background goroutine.

```go
type Logger interface {
	Log(ctx context.Context, message string) error
	Close() error
}

type AsyncLogger struct {
	messages chan string
	done     chan struct{}
	output   io.Writer
	once     sync.Once
}
```

Start the worker in the constructor:

```go
func NewAsyncLogger(output io.Writer, bufferSize int) *AsyncLogger {
	logger := &AsyncLogger{
		messages: make(chan string, bufferSize),
		done:     make(chan struct{}),
		output:   output,
	}
	go logger.run()
	return logger
}
```

The worker owns channel consumption:

```go
func (l *AsyncLogger) run() {
	defer close(l.done)
	for message := range l.messages {
		fmt.Fprintln(l.output, message)
	}
}
```

Cancellation-aware submission prevents a caller from waiting forever when the buffer is full:

```go
func (l *AsyncLogger) Log(ctx context.Context, message string) error {
	select {
	case l.messages <- message:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

## 10. Graceful Logger Shutdown

Shutdown must follow a clear ownership rule: the component that owns the logger closes it after no producer can submit more messages.

```go
func (l *AsyncLogger) Close() error {
	l.once.Do(func() {
		close(l.messages)
		<-l.done
	})
	return nil
}
```

The sequence is:

```text
Stop accepting CLI work
    -> close the messages channel
        -> logger drains accepted messages
            -> logger goroutine exits
                -> Close returns
```

Important rules:

- never close the channel from the receiving goroutine;
- never call `Log` after shutdown has started;
- make `Close` idempotent with `sync.Once`;
- wait for the worker to finish so accepted messages are not lost;
- define and test the behavior of concurrent `Log` and `Close` calls.

For a production-strength implementation, guard the accepting/closed lifecycle with synchronization so a send cannot race with channel closure.

## 11. Context Propagation

Pass `context.Context` from the application boundary to downstream operations:

```text
main/handler -> service -> repository/logger
```

Accept it as the first parameter:

```go
func (s *UserService) Delete(ctx context.Context, id int) error
```

Check cancellation around operations that may block:

```go
select {
case messages <- message:
	return nil
case <-ctx.Done():
	return ctx.Err()
}
```

`context` does not forcibly stop a goroutine. The goroutine or called API must observe `ctx.Done()` and return.

## 12. Dependency Injection and Composition Root

`main` is the composition root. It constructs concrete dependencies and injects them into higher layers.

```go
func main() {
	repository := repository.NewMemoryUserRepository()
	logger := logger.NewAsyncLogger(os.Stdout, 32)
	service := service.NewUserService(repository, logger)
	handler := handler.NewUserHandler(service, os.Stdin, os.Stdout)

	handler.Run(context.Background())

	if err := logger.Close(); err != nil {
		fmt.Fprintln(os.Stderr, "close logger:", err)
	}
}
```

The handler should depend on a small service interface, not `*MemoryUserRepository`.

```go
type UserUseCases interface {
	Create(ctx context.Context, user *model.User) error
	List(ctx context.Context) ([]*model.User, error)
	Find(ctx context.Context, id int) (*model.User, error)
	Update(ctx context.Context, id int, name, email string) error
	Delete(ctx context.Context, id int) error
	Filter(ctx context.Context, term string) ([]*model.User, error)
}
```

## 13. End-to-End Request Flow

For “Add user,” the execution flow should be:

```text
User selects menu option 1
    -> handler reads ID, name, and email
        -> service validates/co-ordinates the use case
            -> repository locks and stores a copy
                -> service submits a log message
                    -> logger goroutine writes the message
                        -> handler prints success
```

Each layer has one primary reason to change:

- terminal format changes affect the handler;
- business workflow changes affect the service;
- storage changes affect the repository;
- logging implementation changes affect the logger.

## 14. Testing Strategy

### Repository tests

Test:

- create, find, list, update, delete, and filter;
- duplicate IDs and missing users;
- trimming and validation;
- insertion-order preservation;
- defensive copies;
- concurrent reads and writes with `go test -race`.

### Service tests

Inject a fake repository and fake logger. Verify:

- repository errors remain discoverable with `errors.Is` or `errors.As`;
- operation context is added with `%w`;
- successful changes generate log events;
- failed changes do not report false success.

### Handler tests

Use `strings.NewReader` for scripted input and `bytes.Buffer` for output. Verify menu flow, validation messages, success messages, EOF, and exit.

### Logger tests

Verify:

- messages are written;
- accepted messages are drained before `Close` returns;
- cancellation releases blocked submission;
- `Close` can be called more than once;
- the logger goroutine exits;
- race detection reports no send/close race.

## 15. Validation Commands

Run from the project root:

```bash
gofmt -w .
```

## 17. Key Takeaways

- Object-oriented Go means composition with structs, methods, constructors, and interfaces—not copying a Java class hierarchy.
- Interfaces should usually be small and defined where their behavior is consumed.
- A `sync.RWMutex` protects shared repository memory; a channel coordinates the logger's message flow.
- Concurrency requires ownership and lifecycle rules, especially for closing channels.
- Custom errors communicate domain meaning, while `%w` preserves the original cause.
- Dependency injection makes each layer easier to replace and test.
- Passing ordinary tests is not enough; concurrent code must also pass the race detector.
